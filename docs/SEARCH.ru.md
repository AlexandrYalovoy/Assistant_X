# Поиск Assistant X

Локальный поиск, через который Claude работает с библиотекой: поиск по словам с учётом словоформ и словарём
сокращений, поиск по смыслу (модель bge-m3) и переранжирование лучших фрагментов (bge-reranker-v2-m3).
Claude подключается к нему как к MCP-серверу `assistant-x` и получает команды `search_library`, `read_pages`,
`page_image`, `book_map`, `verify_quote`, `document_info`, `list_documents`, команды пакетов баз `base_*` и команды разбора `intake_*`
([`assistant_x/server/intake_tools.py`](../assistant_x/server/intake_tools.py)).

Коротко: после того как разбор добавил документы, `assistant-x build` обновляет поисковую базу, а `assistant-x embed`
вычисляет эмбеддинги новых фрагментов (MCP-команда `intake_apply(confirm=True, token=…)` выполняет и то, и другое).

## Где что лежит

```
<code folder>\              the program: assistant_x\ (the package), Setup.bat, intake.bat, assistant-x.bat (a
                            development checkout keeps .venv\ here)
<workspace>\                your data (Documents\Assistant X by default; assistant-x init makes it)
  assistant_x.toml          settings ([search], [intake], [paths]); assistant_x.local.toml: this PC only
  library\                  the originals (for page_image)
  index\                    cards\<code>.json, texts\, CATALOG.md and sources_to_update.md (made from the cards)
  questions.md              your own control questions for assistant-x eval (optional)
  .assistant_x\
    db\                     library.sqlite (catalog + fragments + word index), vectors.f16 (embeddings)
    db\vector_cache\        the embeddings by content: a fragment the model has read once is never computed again
    models\                 only in a workspace of before 2026-10-25 (or a link): its models
    debug\                  journals of failures and calls, debug reports, query reviews
%USERPROFILE%\.assistant_x\  per PC: app\<version> and venv\ (the program, from a medium), models\ (bge-m3,
                            bge-reranker-v2-m3, onnx\: everything works without internet), programs\ (of the
                            intake), the machine lock heavy.lock and its journal heavy.log, mcp_server.lock,
                            speed.json, model_fingerprints.json
```

Какую рабочую папку использует команда: `AX_WORKSPACE`, иначе папку `AX_CONFIG`, иначе ближайшую папку с
`assistant_x.toml`, начиная с текущей и выше, иначе `Documents\Assistant X` ([`assistant_x/core/workspace.py`](../assistant_x/core/workspace.py)).
Синонимы берутся из профиля предметной области ([`assistant_x/profiles/oil-gas-ru/synonyms.txt`](../assistant_x/profiles/oil-gas-ru/synonyms.txt)), если
`[search] synonyms` не указывает ваш собственный файл. В [`assistant_x/core/formats.py`](../assistant_x/core/formats.py) описаны форматы файлов проекта
(маркеры страниц, события, виды файлов по расширению);
карточки — это [`assistant_x/core/card.py`](../assistant_x/core/card.py) и JSON Schema [`assistant_x/schemas/card-1.json`](../assistant_x/schemas/card-1.json) ([docs/INTAKE.md](INTAKE.ru.md), раздел «Карточки»).

## Сборка (один раз, затем после каждого разбора)

[`Setup.bat`](../Setup.bat) выполняет шаги 1 и 2 (сам разбор описан в [`docs/INTAKE.md`](INTAKE.ru.md)); остальное предлагает применение разбора.

1. Python 3.11+ и пакет с поиском по смыслу: `pip install -e ".[dense,intake]"` в папке с кодом.
   Для RTX 50xx нужна сборка PyTorch с CUDA 12.8+, установленная заранее:
   `pip install torch --index-url https://download.pytorch.org/whl/cu128`. Без дополнения `dense` поиск работает только
   по словам.
2. `assistant-x download-models` — модели в `.assistant_x\models` рабочей папки (≈ 4.5 ГБ, один раз).
3. `assistant-x build` — поисковая база и индекс слов, а также заново созданные из карточек `CATALOG.md` и
   `sources_to_update.md`. Обновляются только изменившиеся документы: в тексте, у которого изменился sha256 (вместе с
   его `.pages.json`), заново нарезаются на фрагменты только страницы с изменившимся текстом или фрагментами —
   фрагменты остальных страниц сохраняют свои номера и эмбеддинги, поэтому исправленная вручную страница стоит
   вычисления эмбеддингов только этой страницы; карточка с изменившимся sha256 (`docs.card_sha`) читается заново;
   `--full` пересобирает всё. Сначала выполняется проверка индекса (`assistant-x check`, см. «Проверка индекса») и
   при ошибках в карточках сборка останавливается. Без карточек получается пустая база.
   Если программа изменила формат базы (последний раз: страницы и точный индекс, схема базы 3, октябрь 2026),
   она сама попросит `--full`.
4. `assistant-x embed` — эмбеддинги новых фрагментов (на видеокарте, float16) и обновление индекса FAISS.
   После замены многих документов: `assistant-x embed --compact`. После `assistant-x build --full` эмбеддинги берутся
   из кэша векторов (ниже), и если там есть все фрагменты, модель даже не загружается. Полная сборка пишет новый файл `.assistant_x\db\library-<time>.sqlite`, а поиск до конца
   пользуется предыдущей базой: новая ждёт своих эмбеддингов (её имя — в `library.next`), и `embed`, вычислив их,
   переключает поиск на неё (`library.current`); старый файл удаляется, как только его никто не держит.
   База работает в режиме WAL: поиск читает, пока сборка пишет.
5. `assistant-x eval` — проверка на ваших собственных контрольных вопросах (`questions.md` в рабочей папке: таблица
   `| question | code:pages; … |`, группы задаются `## headings`): таблица метрик по группам (документ и страница в
   первых 10, MRR, все места ответа). `--fast` — только по словам, без модели; `--check` сравнивает с сохранённым
   прогоном `eval_baseline.json` и завершается с ошибкой, если стало хуже, `--save` записывает новый прогон.
   В строке может быть третья ячейка: точная фраза со страницы ответа в кавычках,
   `| what is the allowable gas velocity? | L-00015:12 | "the allowable velocity of the gas" |`. Столбец «Цитаты»
   показывает долю таких вопросов, у которых фраза стоит на странице ответа среди первых результатов (сравнение по
   скелету `verify_quote`, см. ниже); `--check` и `--save` учитывают и его. Кроме вопросов по вашим темам, стоит
   написать две группы:
   - `## Designations` — вопросы, называющие документ или марку по обозначению в тех написаниях, которые набирают
     пользователи: `GOST 1510-84`, `GOST R 51858-2002` в любой раскладке, марка стали с похожими латинскими буквами, шифр с дефисом или косой чертой;
     ответ — страница, на которой стоит обозначение.
   - `## Quotes` — вопросы с фразой в третьей ячейке, взятой дословно со страницы ответа (предложение пункта,
     строка таблицы): они показывают, что текст страницы находится и читается точно, а не только её тема.

Проверить поиск вручную: `assistant-x search "glycol carry-over from the absorber"` (`--section N`, `--code L-00015`,
`--doc-type handbook`, `--lang ru`, `--rerank`).

## Проверка индекса и состояние библиотеки

- `assistant-x check` проверяет каждую карточку по схеме (языки, обязательные для каждого текста, полки, ограничения)
  и сверяет карточки, тексты и оригиналы: карточка не в формате JSON или с именем файла, не совпадающим с её
  шифром; нет текста документа или части, которые называет карточка; нет оригинала на его месте в библиотеке; один
  файл на два документа; формат текста ([docs/INTAKE.md](INTAKE.ru.md), «Формат текста»): маркеры страниц не по порядку или не на каждую
  страницу исходного PDF. Ошибки останавливают `assistant-x build`; предупреждения (тексты с потерянными символами,
  пустые страницы, лишние тексты, другие редакции не из библиотеки, окончания строк CRLF, невидимые символы,
  отсутствующий `.pages.json` или с другими страницами, чем в его тексте) только перечисляются. `--all` — все случаи,
  `--no-files` — без проверки оригиналов.
- При сборке база запоминает язык текста и его качество (скан, потерянные символы, пустые страницы, оценку
  распознавания из `index\ocr_quality.tsv` — столбец `docs.ocr_score`, ниже 70 она попадает в примечание), а также
  открытые вопросы его карточки. Claude видит это рядом с фрагментом и в `document_info` как строку
  «Source quality».
- `assistant-x report` ([`scripts\library_report.bat`](../scripts/library_report.bat)) раз в месяц: сводка по разделам, ошибки индекса, качество текстов, тексты, которые стоит распознать заново, открытые пункты для обновления, книги
  без оглавления в карте, издания до 1990 года и манифест оригиналов. Отчёт сохраняется в
  `.assistant_x\debug`.
- `python -m assistant_x.intake.manifest` ведёт `index\manifest.tsv`: путь, размер, дата и SHA-256 каждого файла `library` с
  его шифром. Обновляйте его после применения новых документов; `--check` пересчитывает все хеши и показывает
  повреждённые или пропавшие файлы (например, после восстановления из резервной копии).

## Подключение вручную

Если установщик не подходит: Python 3.11+, `pip install -e ".[dense,intake]"` в папке с кодом (видеокарта не
нужна; ставится обычный PyTorch), `assistant-x init` и `assistant-x skill`. Переранжирование (`"rerank"` в `assistant_x.toml` `[search]`) по умолчанию `"auto"`: для каждого вопроса на видеокарте
(CUDA или DirectML), если модель `bge-reranker-v2-m3` лежит в `models`. Оно упорядочивает кандидатов, а гибридная
оценка разрешает равенства (`final = fused / max(fused) + rerank_weight · sigmoid(logit)`, `rerank_weight = 100`): на 80
контрольных вопросах по настоящим документам страница оказывалась первой 57 раз вместо 45 при весе 1 версии 0.5.4
(MRR 0,705 → 0,801; на процессоре 44 → 54), на вопросах 87 карточек MRR документа 0,484 → 0,512. Вес 1 заставляет
переранжирование лишь уточнять гибридный порядок (стенд [`tests/search/quality.py`](../tests/search/quality.py)
проверяет устройство поиска на поддельных моделях, а не этот выбор). Без видеокарты оно занимает секунды на вопрос и не включается;
`true` / `false` — всегда / никогда.

**Claude Desktop:** добавьте в `%APPDATA%\Claude\claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "assistant-x": {
      "command": "C:\\Assistant_X\\.venv\\Scripts\\python.exe",
      "args": ["-m", "assistant_x.server.mcp_server"],
      "env": { "HF_HUB_OFFLINE": "1", "AX_WORKSPACE": "C:\\Users\\you\\Documents\\Assistant X" }
    }
  }
}
```
**Claude Code:** `claude mcp add assistant-x --scope user -e HF_HUB_OFFLINE=1 -e "AX_WORKSPACE=<workspace>" -- "<code folder>\.venv\Scripts\python.exe" -m assistant_x.server.mcp_server`

После перезапуска Claude команды библиотеки появятся в списке инструментов.

Сервер загружает смысловую модель в фоне (около 10 с, с пробным запросом для прогрева видеокарты).
Пока она загружается, `search_library` отвечает сразу, только по словам, с пометкой «the semantic search is still
loading, repeat the query in 10 s» (смысловой поиск ещё загружается, повторите запрос через 10 с).

## Если что-то сломалось: отладочный отчёт

- Все сбои сервера и скриптов записываются в `.assistant_x\debug\failures.log` (с трассировкой), каждый вызов
  команды библиотеки — строкой в `calls.log` (время, длительность, результат, аргументы). Файлы сами урезаются до 1–2 МБ.
- Когда команда завершается сбоем, Claude получает не голое «Error executing tool», а текст ошибки и подсказку, как
  сделать отчёт.
- **Отчёт:** дважды щёлкните [`scripts\debug_report.bat`](../scripts/debug_report.bat). Через 1–2 минуты в `.assistant_x\debug` появится
  `debug_report_<PC id>_<date>.md`, папка откроется сама. Именно этот файл и нужно отправить. Быстрый вариант без
  загрузки моделей: `scripts\debug_report.bat --quick`.
- В отчёте: ПК (ОС, процессор, память, диски, видеокарта), версии Python и пакетов, видит ли torch
  видеокарту, файлы установки с контрольными суммами (по ним видно, какая версия установлена), assistant_x.toml и
  проверка всех путей, состояние базы и эмбеддингов, подключение в Claude Desktop и его журнал по
  assistant-x, самопроверка каждого слоя поиска с её временем (слова, смысл, переранжирование, изображение страницы,
  запуск MCP-сервера), последние сбои и вызовы, а в самом начале — список найденных проблем.
- Чего в отчёте нет: содержимого документов и других настроек Claude (от других серверов видны только их
  имена). В нём есть имена ПК и пользователя, пути и тексты последних запросов к библиотеке.
- Если Python на ПК не найден, окно сообщит об этом: тогда достаточно снимка экрана с этим окном.

## Обзор запросов: учимся на реальных вопросах

[`scripts\query_log.bat`](../scripts/query_log.bat) (или `assistant-x query-log [journals of other PCs…]`) создаёт в `.assistant_x\debug` файл
`query_log_<PC id>_<date>.md`:
- сводка по командам: сколько вызовов, сбоев и сколько времени они заняли;
- **слабые запросы**: лучший фрагмент по смыслу ближе, чем 0.5, или по словам ничего не нашлось. Это кандидаты
  на новые документы или на новые строки в `synonyms.txt`;
- **долгие поиски**: 4 и более поиска подряд по одному вопросу, то есть нужное нашлось не сразу;
- медленные вызовы, все запросы и черновик строк для `questions.md` (ответ, то есть шифр и страницы, заполняет
  специалист, после чего вопрос участвует в `assistant-x eval`).
Та же сводка входит в отладочный отчёт. Записи без близости и числа
совпадений учитываются только в общих цифрах.

«Low closeness» над результатами `search_library` говорит о том, что в библиотеке, возможно, нет ответа на вопрос.
Признаков два: близость лучшего фрагмента по смыслу ниже порога (и переранжировщик тоже не уверен) или половины
значимых слов вопроса (без стоп-слов, приведённых к основе, как в индексе слов; синоним засчитывается за слово) нет ни
в одном из 5 лучших результатов («the library has nothing on «…»»). Порог — `[search] weak`, если он задан; иначе,
когда в журнале этого ПК набралось 30 вопросов с ответами, — 10-й процентиль их близости в пределах 0.35–0.6
(вычисляется один раз при запуске сервера); иначе 0.5.

## Как это работает

- База (схема 3) хранит текст каждой страницы точно в том виде, в каком он записан в `index\texts\<code>.md` (таблица `pages`,
  с печатной меткой, источником, оценкой распознавания и флагами из её `.pages.json`, [docs/INTAKE.md](INTAKE.ru.md), «Формат текста»).
  `read_pages` возвращает его без изменений, а найденный фрагмент показывает именно текст своей страницы. Найденный
  фрагмент и `read_pages` показывают печатную страницу по меткам страниц PDF (`p. 218 (PDF 222)`; без меток — по
  нумерации страниц из карточки) и строку «Page:» для страницы со сложной таблицей или плохим распознаванием.
- Текст каждой страницы режется на фрагменты по 1–2 абзаца (таблица Markdown остаётся целой); фрагмент не
  пересекает границу страницы, поэтому ссылка всегда точна. Фрагмент — это диапазон символов своей страницы
  (`chunks.start`, `chunks.end`): фрагменты страницы по порядку и составляют саму страницу. Текст, по которому фрагмент
  ищется и по которому вычисляется его эмбеддинг, отличается от текста страницы только в трёх местах: перед ним стоит
  заголовок его раздела; кусок длинной таблицы, разрезанной по строкам, начинается с шапки таблицы, а кусок длинного
  текста, разрезанного надвое, — с последнего предложения предыдущего куска (`chunks.lead`: в тексте для поиска, но
  никогда в странице или в результатах); эмбеддинг вычисляется по тексту без разметки Markdown (`**`, `#`, обратные
  кавычки; `[search] table_rows = true` в assistant_x.toml ещё и превращает таблицу в строки вида «заголовок: значение; …»).
  У карточки и у единицы есть собственный текст (`chunks.own_text`).
- Каждый фрагмент помнит раздел, в котором стоит: цепочку нумерованных заголовков и последний ненумерованный
  («11.9. Оценка фактических потерь / 11.9.2. Потери при истечении…»). Заголовки берутся из разметки Markdown;
  повторяющиеся колонтитулы, оглавления и пустые заголовки вроде «Решение» пропускаются. Раздел участвует
  в поиске по словам и по смыслу и показывается Claude в результатах, поэтому абзац глубоко внутри главы
  находится и по её теме.
- Поиск по словам: SQLite FTS5 по основам слов (Snowball, стеммеры языковых пакетов: русский и английский) +
  группы синонимов из `synonyms.txt` профиля. У индекса слов есть второй столбец, `exact`: целые лексемы
  текста в нижнем регистре, обозначение — одна лексема вместе с дефисом, точкой или косой чертой (`1510-84`, `51858-2002`, `5.3`),
  похожие буквы двух алфавитов — как одна (`homoglyphs` языковых пакетов: латинские X, H или T в кириллической
  марке стали). Обозначения карточек, названные в вопросе, его фразы в кавычках и его шифры с цифрами
  (`GOST 5632-2014`, `12X18H10T`) ищутся там как фразы, рядом с основами: `stem : (…) OR exact : (…)`.
- Слишком частые слова запроса (более чем в 5 % фрагментов, например «нефть», «расчёт») не попадают в
  поиск по словам: на ранжирование они почти не влияют, а на большой базе замедляют его во много раз (`common_term_share` в
  assistant_x.toml).
- Поиск по смыслу: косинусная близость к векторам фрагментов (`vectors.f16`, float16). До 200 тысяч
  фрагментов это точный перебор; больше — `assistant-x embed` сам строит индекс FAISS (`vectors.f16.ivfpq.faiss`, нужен
  пакет `faiss-cpu`): кандидаты берутся из индекса и пересчитываются точно. Фильтр (шифры, разделы,
  жанры, языки, годы) применяется до поиска: если он пропускает до 100 тысяч фрагментов, они сравниваются
  точно, если больше — поиск идёт внутри индекса только среди них (FAISS `IDSelectorBatch`).
- Списки смешиваются (Reciprocal Rank Fusion); лучшие max(50, 4k) образуют пул: вторая модель переранжирует их, затем
  один документ даёт не более 3 страниц результатов, чтобы были видны разные источники. Обозначение, названное в
  вопросе, ставит свою карточку первой после переранжирования. Смысловая модель и переранжировщик читают один и тот же текст
  фрагмента (`common.model_text`: краткое название документа, заголовок раздела, текст без Markdown).
- Карточки — тоже фрагменты (`chunks.kind`): карточка каждого документа, по фрагменту на каждый язык карточки
  (`card`: обозначение, название, ключевые слова и термины на этом языке, область применения и аннотация, страница 0), один — для её
  вопросов и тем (`card_q`, вес 1.0: `[search] card_q_weight`; вместе с фрагментами `card` — единый результат
  вида `card`), а также единицы выпуска журнала
  или сборника трудов (`unit`: название, авторы и аннотация статьи, на её первой странице). Поэтому английский
  вопрос находит русский документ по его карточке, и наоборот; карточка учитывается с весом 0.7
  (`[search] card_weight`), поскольку не ссылается на страницу, и показывается как `[code, card]`.
- Обозначение, названное в вопросе (`GOST 1510-84`, `ГОСТ 1510-84`, с любыми пробелами и тире), ставит карточку этого
  документа первой; термины карточек (сокращение, его название на каждом языке, его расшифровка) входят в группы
  синонимов; фрагмент внутри главы из оглавления своей карточки (таблица `toc`, с последней страницей каждой записи),
  название которой содержит половину слов вопроса, поднимается на четверть (`[search] toc_boost`).
- Фильтры: раздел (полка — по её букве, папке или названию на английском или русском, так что «Datasheets» находит и
  «Datasheets and catalogs»), шифры, жанры (`doc_types`), языки документов (`langs`), годы.
  Действует ли документ — не дело поиска: в библиотеке лежат те редакции, которые выбрал пользователь (карточка
  называет другие редакции, хранящиеся рядом).
- Обозначения, на которые ссылается карточка, попадают в таблицу `links` вместе с шифром документа библиотеки, у которого
  это обозначение (пусто, если такого в библиотеке нет).
- Документ из нескольких файлов (в его карточке есть `file.parts`): файл карточки и текст `<code>.md` — это сам
  документ (файл -01 его папки), остальные файлы — части со своим шифром `<code>-NN`, своим текстом
  `<code>-NN.md` и своей нумерацией страниц PDF. В результатах и ссылках часть называется так же:
  [E-00006-02, PDF 3]. Фильтр по шифру документа ищет и в его частях; `list_documents` показывает только
  документы, `document_info` для части показывает карточку её документа.
- `verify_quote(code, page, text)` проверяет цитату, прежде чем Claude возьмёт её в кавычки (навык требует этого
  перед дословной цитатой и перед числом, взятым из таблицы): цитата и страница сравниваются по их
  скелету (`common.skeleton`: NFKC, нижний регистр, свёртка языков и похожих латинских и кириллических
  букв, любое тире как «-» и любая кавычка как двойная по таблицам `dashes` и `quotes` языковых
  пакетов, мягкий перенос и разметка Markdown отброшены, пробелы схлопнуты) — на самой странице, затем на предыдущей
  и на следующей. Слово в слово: «found» (или «found_nearby» на соседней странице, которую тогда и нужно
  цитировать); иначе ищется ближайшая последовательность слов трёх страниц по `difflib.SequenceMatcher`: сходство 0.9 и выше —
  найдено с небольшими отличиями (отличия перечисляются, например «450» → «400»), меньше — «not found» с ближайшим
  местом, и цитата идёт в ответ как пересказ. В ответе также есть печатная страница и строка «Page:»
  для сложной таблицы или плохого распознавания этой страницы.
- `page_image` берёт изображение страницы из library (для DOC/DOCX — из лежащей рядом PDF-копии), а если документ
  ещё не перемещён, ищет файл с тем же именем по всей библиотеке. Для DOC/DOCX нужна PDF-копия с тем же
  именем рядом.
- Карта книги (`bookmap.py`, с 2026-10-22; структура читается из текста модулем `core/textmap.py`, которым
  разбор пользуется и для оглавления карточки): при сборке каждый документ запоминает своё оглавление (нумерованные
  разделы и главы с диапазонами страниц PDF) и где в нём таблицы, рисунки, формулы и приложения (подпись
  «Table 4.2», номер формулы «(12)» в конце строки, первое место вне оглавления). Подписи
  и слова ссылок берутся из языковых пакетов (`lang/<code>/references.json`: «Table 4.14», «see
  table 4.14», «formula (9.8)», «see fig. 1.5», «cl. 5.3» и их русские формы). Когда
  найденный фрагмент ссылается на такой объект, в результатах появляется строка «References: … → PDF N», и Claude читает нужную страницу тоже.
  Команда `book_map` (и `python -m assistant_x.search.bookmap L-00015 --page 300`) показывает оглавление вокруг страницы и то, что
  лежит в её разделе. Карта строится по базе, без моделей, за минуты; у сканов с плохим распознаванием
  оглавление получается беднее.

## Производительность (измерено 2026-10-20 на тестовой библиотеке)

Тогда: 24 документа (0.76 ГБ оригиналов) = 9.2 тысячи страниц = 26 тысяч фрагментов. 200 ГБ — это примерно 2.4 миллиона
страниц и 7 миллионов фрагментов (больше, если у многих PDF есть текстовый слой: в них больше текста на мегабайт).

| Что | 26 тысяч фрагментов | 1 миллион (измерено) | 7 миллионов (оценка) |
|---|---|---|---|
| Поиск по словам | 0.01–0.04 с | 0.1–0.2 с (до исправления 0.6–1.5 с) | ~1 с |
| Поиск по смыслу, точный перебор | 0.04 с | 3 с | 20+ с — непригодно |
| Поиск по смыслу, FAISS | — | 3 мс | ~5–10 мс |
| База library.sqlite | 53 МБ | 2 ГБ | ~14 ГБ |
| Эмбеддинги vectors.f16 | 54 МБ | 2 ГБ | ~14 ГБ (+0.5 ГБ индекс) |
| Вычисление эмбеддингов на RTX 5080 | 11 мин fp32, 3.5 мин fp16 (измерено) | ~7 ч fp32, ~2 ч fp16 | ~2 дня fp32, ~14 ч fp16 |

Измерено на виртуальной машине с 4 ядрами; на настольном ПК поиск по словам был в 2–3 раза быстрее. fp16 на ПК в 3.4 раза быстрее
fp32 (61 против 18 фрагментов/с на самых длинных фрагментах), векторы совпадают с fp32 (косинус ≥ 0.99997, точнее,
чем само хранение во float16). На ПК (26 тысяч фрагментов): первый запрос ~7.6 с (загрузка модели), затем
0.06 с; только по словам 0.002 с.

### Цена одного вопроса (профилировано 2026-10-26)

Синтетическая библиотека из 3000 документов по 9 страниц (36 138 фрагментов), RTX 5080 Laptop с CUDA (общая с
другим сервером, занимавшим 7 ГБ её памяти), переранжировщик включён, `k = 8`; 1000 случайных вопросов из 2–6 слов после прогрева
(17 с: обе модели), `Library.search` профилирован cProfile на первых 100:

| Показатель | Значение |
|---|---|
| Задержка | p50 900 мс, p95 976 мс, максимум 1.9 с |
| Переранжировщик (50 кандидатов, `POOL`) | 0.80 с из 0.885 с на вопрос (90 %); большая часть — ожидание видеокарты, пока пакеты идут на неё и обратно |
| Поиск по смыслу (эмбеддинг запроса + FAISS) | 0.07 с |
| Поиск по словам и оценка строк | 0.05 с |
| Память процесса (RSS) | 2533 МБ после прогрева, 2564 МБ после 100 вопросов, 2574 МБ после 1000 |

Память растёт, пока заполняются кэши (первые ~100 вопросов), а затем не меняется: утечки нет. Цену вопроса
определяет переранжировщик; `rerank = false` (или `"auto"` на процессоре) отвечает примерно за 0.1 с ценой порядка
найденного. Ранжирование для этого измерения не менялось.

## Видеокарты AMD и Intel: DirectML (`onnx_models.py`)

`assistant_x.toml` `[search]`: `backend` — `auto` (по умолчанию: CUDA, если есть; иначе DirectML на видеокарте не NVIDIA с 2 ГБ
собственной памяти и более; иначе процессор), `torch` (только torch), `onnx-dml` (всегда DirectML, если есть пакет
и модели); `dml_device` — номер адаптера DirectML (`python -m assistant_x.search.onnx_models --adapters`;
нумерация по производительности: дискретная карта первая). Модели ONNX (fp32, по 2.1 ГБ каждая) — это
`.assistant_x\models\onnx\<model>\model.onnx` + `.data`; соберите их командой `python -m assistant_x.search.onnx_models --export` (под
блокировкой, ≈30 с; нужно дополнение `export`: onnx и onnxscript, без интернета из `.assistant_x\packages\wheels_dml`). Векторы ONNX совпадают с torch (косинус 1.0000 на 100
фрагментах, ≥ 0.9997 к базе), поэтому база общая. Пакет `onnxruntime-directml` заменяет `onnxruntime`
(`install.py` делает это сам, если выбрал DirectML).
Измерено 2026-10-24 (100 фрагментов / запрос / переранжировщик на 50 кандидатах): CUDA fp16 1.2 с / — / 0.34 с; DirectML на
RTX 5080 6.8 с / 89 мс / 2.0 с; DirectML на встроенной Intel (Core Ultra 9 275HX) 121 с / 327 мс / 25 с; процессор
93 с / 62 мс / 28 с. Контрольные вопросы через DirectML без CUDA — как на CUDA (97 % / 86 % / MRR 0.66).

## Кэш векторов (`vector_cache.py`)

`.assistant_x\db\vector_cache\` хранит каждый вектор, который `embed` вычислил или нашёл в базе, под ключом
sha256(отпечаток модели, вид фрагмента, текст, который модель из него читает, — `common.model_text`). Фрагмент,
текст которого не изменился, берёт вектор оттуда: после `build --full`, после того как документы получили новые шифры (установлен пакет
базы), в новой базе той же рабочей папки. Векторы базы, эмбеддинги которой вычислены до появления кэша, заносятся в
него первым `embed` (один раз: `meta vector_cache_seeded`) или отдельно командой `assistant-x embed --seed-cache`;
никогда — под ключом другой модели (отличается имя или `meta embed_fingerprint`). `embed --compact` также удаляет
векторы кэша, которые больше не использует ни одна база.

Отпечаток модели обозначает векторы, которые даёт модель: её имя, sha256 её `config.json` и `tokenizer.json`,
sha256 её весов (тот, что HuggingFace записал рядом со скачанным в `.cache\huggingface\download`, иначе вычисленный
один раз и хранящийся для каждого ПК в `%USERPROFILE%\.assistant_x\model_fingerprints.json`; в папку модели никогда
ничего не пишется) и `max_seq_length` (текст, обрезанный на другой длине, даёт другой вектор). База запоминает его
(`meta embed_fingerprint`); пакет базы несёт его вместе со своими векторами.

## Одна база — одна модель; int8 на процессоре (`models.py`)

Эмбеддинги базы навсегда вычисляются одной моделью (`meta embed_model`, имя папки модели, например `bge-m3`): библиотека,
которую вы собираете, и библиотека, которую вы устанавливаете и дополняете, смешивают свои векторы, поэтому `assistant-x embed` отказывается добавлять векторы в
базу другой модели («The base was embedded with X, this workspace is set to Y; one base, one model.»), а
поиск сообщает об этом и отвечает по словам. Ускорения сохраняют векторы: float16 на видеокарте, DirectML, а на
процессоре — bge-m3 в int8 ONNX (`python -m assistant_x.search.onnx_models --int8` записывает
`models\onnx\bge-m3\model.int8.onnx` и сразу его проверяет: на 200 фрагментах базы или на примерах предложений
языковых пакетов средний косинус к векторам float32 должен быть не меньше 0.99, а каждый — не меньше 0.97, иначе файл удаляется;
`[search] cpu_int8 = true` включает его; по умолчанию выключено с 0.2: его векторы примерно на 2 % отличаются от векторов полной модели). `search/models.py` — единственное место, где загружаются модели, и для `embed`, и для
поиска. Оценки времени (`embed` на процессоре, `intake_reindex`) используют скорости, измеренные на этом ПК
(`speed.json` в `%USERPROFILE%\.assistant_x`: каждый `embed` от 50 фрагментов, а также `--check`). Измерено 2026-10-25 (200 фрагментов
библиотеки, 120 русских и 80 английских, Core Ultra 9 275HX): int8 принимается, только если средний косинус к векторам torch float32
не меньше 0.99, а каждый — не меньше 0.97; один масштаб на тензор дал 0.980 (минимум 0.972), масштаб на канал
0.983 (минимум 0.970), на канал с первым и последним слоем во float32 — 0.984 (минимум 0.970): всё отвергнуто, поэтому
на процессоре остаётся float32 (1.3 фрагмента/с в ONNX float32, 2.2 в int8).
